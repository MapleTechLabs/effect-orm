MySQL and MariaDB generated columns: `MySQL.column(type, { generated: { as, stored? } })` declares a `GENERATED ALWAYS AS (<as>) STORED | VIRTUAL` column. `as` is SQL, or a DSL callback that may read the row's columns. The column is computed, as a ClickHouse `MATERIALIZED` one is: an insert row, an update SET or `onDuplicateKeyUpdate` that writes it is a type error and refused at runtime, `excludedAll` skips it, and `tableSchemas(table).insert` / `.update` leave it out; selects read it. It works on `external: true` tables, where it only marks the column computed, so an insert into a table another tool owns no longer sends a column MySQL refuses. On an owned table the DDL writes `` `col` <type> GENERATED ALWAYS AS (<expr>) STORED|VIRTUAL `` with no `NOT NULL` (MariaDB refuses it there) and no default; a `default`, `defaultExpr`, `defaultFn` or `onUpdate` beside it is a type error and a definition problem, as is a generated primary key column or one reading a later generated column or itself. `effect-orm generate` creates and adds such columns, `MODIFY`s a changed expression, and drops and adds back (in one `ALTER TABLE`, with its indexes around it) a column that becomes or stops being generated, or changes between STORED and VIRTUAL; a base column's values lost that way need `confirm_data_loss`. `MySQL.ComputedColumnsOf` and `MySQL.GeneratedColumn` are new types, and `MysqlSchemaTable` takes the computed columns as a new last type parameter. `MysqlColumnEntity` has an optional `generated: { expr, stored }`, absent on other columns, so existing snapshots keep their ids.
